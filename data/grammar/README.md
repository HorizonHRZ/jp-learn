# 语法数据格式说明 —— 怎么往里加内容

> 这个目录里的 JSON 是**内置数据**（属于"程序"那一层），和你的学习数据（浏览器 IndexedDB）完全分开。
> 加内容**不需要改任何代码**，写完 JSON 刷新页面就能看到。
>
> 当前是「丙」阶段：**框架已搭好，内容先放 10 条样例**。
> **内容方向已于 2026-10-07 定下**（见第七节）：JLPT 线 + 书面语阅读线**两条并存**。
> 现有 10 条样例属于 JLPT 线的 N5，书面语线还没开始。第二条第 7.4 节给了建议顺序。

---

## 一、目录结构

```
data/grammar/
  index.json     ← 目录索引：只放"列表页要显示的字段"，要小、要快
  N5.json        ← 一个等级一个文件，正文在这里
  N4.json
  N3.json
  ...
```

**为什么要拆成 index + 分等级文件**：目录页只需要 `id/level/category/title/meaning` 这几个字段，
不需要把几百条正文全下载下来。分等级还让以后"只下载我需要的等级"成为可能。
以后条目多了，`index.json` 仍然是几十 KB，打开目录页很快。

---

## 二、`index.json` 的结构

```json
{
  "schema": 1,
  "generatedAt": "2026-10-07",
  "count": 10,
  "levels": ["N5"],
  "categories": ["助词", "时态", "存在", "指示", "愿望"],
  "items": [
    {
      "id": "n5-wa",
      "level": "N5",
      "category": "助词",
      "title": "は（主题）",
      "meaning": "提示句子的主题 ——「关于这个东西，我要说…」",
      "file": "N5.json"
    }
  ]
}
```

> ⚠️ **`index.json` 必须和正文文件保持一致**。它由脚本生成，不要手改：
> `node tools/build-grammar-index.mjs`
> `tools/test-grammar.mjs` 会检查两者是否对得上，对不上就报错。

## 三、正文文件的结构（`N5.json`）

```json
{
  "schema": 1,
  "level": "N5",
  "items": [ { …见下… } ]
}
```

### 单条语法的字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 全局唯一。格式 `等级-短名`，如 `n5-wa`。**改名等于丢用户的学习状态**，定了就别改 |
| `level` | ✅ | `N5` / `N4` / `N3` / `N2` / `N1`。书面语线也照填最接近的等级 |
| `category` | ✅ | 功能分类。见下方「分类取值」 |
| `title` | ✅ | 条目标题，如 `は（主题）` |
| `connection` | ✅ | **接续规则**：前面接什么词形。这是自学最容易错的地方。<br>L4「读法」类填**适用场景**（见 7.3） |
| `meaning` | ✅ | 一句话讲清它干什么（中文） |
| `detail` | | 再展开一点的说明，可省略 |
| `examples` | ✅ | 例句数组，见下。**至少 1 条** |
| `confusions` | | 易混对比数组，见下 |
| `mistakes` | | 常见错误数组（纯字符串） |
| `tags` | | 便于检索的标签（纯字符串） |
| `source` | ✅ | 来源说明，见第五节的**诚实要求** |
| `line` | | `jlpt` / `written`（哪条线）。**不填按 `jlpt` 处理**，界面按 `category` 分组亦可 |

#### 分类取值（`category`）

两条线共用一套分类，界面按它筛选：

| 线 | `category` 取值 |
|---|---|
| JLPT | `助词` `时态` `敬语` `接续` `惯用型` `存在` `指示` `愿望` |
| 书面语 | `书面语`（L1/L2 通用） |
| 文语 | `文语`（L3） |
| 读法 | `读法`（L4，每条是一种**读句子的方法**，不是一个语法点） |

#### `examples` 里每条

| 字段 | 必填 | 说明 |
|---|---|---|
| `ja` | ✅ | 日文原句。**只写日文，不写空格**（空格会让分词退化成单字） |
| `zh` | ✅ | 中文翻译 |
| `note` | | 这条例句在演示什么 |

> **句子的振假名和读音不用你写**。界面会用内置分词器（`tools/tokenizer.js`）
> 在服务端算出来，和歌词页/精读页同一套。少写一份就少一份出错和过期。
> 这也是为什么例句里**不要手动写空格**——见 `app/js/ocrtext.js` 顶部记的那个坑。

#### `confusions` 里每条

| 字段 | 必填 | 说明 |
|---|---|---|
| `with` | ✅ | 和谁容易混，如 `が` |
| `diff` | ✅ | 差别在哪（中文，说人话） |
| `example` | | 一组对照例句，`{ja, zh}` |

## 四、加一条新语法的完整步骤

1. 打开对应等级的正文文件（比如 `N5.json`），往 `items` 数组里加一条
2. 运行 `node tools/build-grammar-index.mjs` 重新生成 `index.json`
3. 运行 `node tools/test-grammar.mjs` 检查格式对不对
4. **刷新浏览器**即可看到（`data/` 是静态资源，不需要重启服务）

加一个新等级（比如 `N4`）：
1. 新建 `N4.json`（可以复制 `N5.json` 改）
2. 更新 `index.json` 里 `levels` 数组 —— **这一步用 `build-grammar-index.mjs` 自动完成**
3. 界面会自动多出一个等级筛选按钮（等级列表是从 `index.json` 读的，不是写死的）

## 五、诚实要求（重要）

`source` 字段**必须如实写**。这块是踩过教训的：项目里别处的数据来源
（`使用说明.md` §四）就明确写了"jmdict-cn 的中文释义是上游用模型生成的，不是人工词典"。

所以：

- 如果内容是我们**自己写的样例** → `"source": "本项目自写样例（非权威教材，仅供演示格式）"`
- 如果**改写自某个开放数据集** → 写清仓库链接 + 许可（如 `CC BY-SA 4.0`），
  并按许可要求署名。**没有核实许可之前不要往里放别人的内容。**
- 如果**手工编写** → `"source": "项目自编"`

**绝不要**把从教材/网站抄来的内容不标来源地放进来。

## 六、为什么状态不在这个目录里

收藏 / 已掌握 / 待复习这些是**你的数据**，存在浏览器 IndexedDB 的 `grammarState` 表里
（`{grammarId, favorite, status, updatedAt}`）。

这个表**早就建好了**，所以做语法功能**不需要动 `SCHEMA_VERSION`、不需要迁移**。
好处是：换电脑时它跟着"导出全部数据"一起走；而这个目录里的正文属于程序，
升级程序不会碰到你的学习状态。

## 七、内容计划（2026-10-07 定的方向）

> 这一节是**给以后接手的人（包括未来的我）看的**。不写下来，内容方向一定会走偏。

### 7.1 为什么不是纯 JLPT

用户的原话需求是：

> 「我觉得看懂就行，主要是我最近在读一些日文原著例如《我是猫》，但感觉晦涩难懂。」
> 后来又补：「保留 JLPT 相关内容，应试日语我也要学；但是关于书面语的阅读也要有，加进去。」

所以**两条线都要**，而且它们是**不同的东西**：

| | JLPT 线 | 书面语阅读线 |
|---|---|---|
| 目的 | 应试、拿级 | 读懂近代书面日语（夏目漱石这类） |
| 语体 | 礼貌体（です・ます）为主 | 常体（だ・である）、文语残存 |
| 粒度 | 一个句型一个点 | 一个句型 + **长句怎么拆** |
| 典型内容 | ～なければならない | ～にほかならない、～ざるを得ない |
| 现有 10 条样例 | ✅ 属于这条线 | ❌ 一条都没有 |

**⚠️ 现有样例全是 JLPT 线的 N5（助词 + 时态），对《我是猫》帮助接近 0。**
这不是"内容还不够多"，是**方向缺了半条**。加内容时两条线要一起加。

### 7.2 四层结构

| 层 | 名称 | 条数（估） | 分类值 | 对《我是猫》的帮助 |
|---|---|---|---|---|
| **L1** | 现代书面语基础 | ~60 | `书面语` | ⭐⭐⭐⭐⭐ 立刻用得上 |
| **L2** | 近代书面语句型 | ~80 | `书面语` / `惯用型` | ⭐⭐⭐⭐⭐ 正中目标 |
| **L3** | 文语残存（漱石高频） | ~40 | `文语` | ⭐⭐⭐⭐ 原著高频 |
| **L4** | **长句拆解方法** | ~10 | `读法` | ⭐⭐⭐⭐⭐ 治"晦涩难懂" |

**JLPT 线在同一套结构里并存**，`category` 用 `助词` `时态` `敬语` `接续` `惯用型`，
`level` 照常填 N5～N1。

### 7.3 各层到底放什么（关键：给例子，不然会写偏）

**L1 现代书面语基础** —— 从"能读"到"读得顺"的最小集合：

- 常体：だ / である / だった / ではない
- 连体修饰（**这是《我是猫》最难的地方**）：动词/形容词直接接名词，
  且可以套很多层 —— 「昨日買ったばかりの本」这类
- 被动 / 使役 / 使役被动（书面语里被动表"客观叙述"的用法）
- 名词化：こと / の / もの
- 书面语连接词：しかし / ゆえに / したがって / ところが
- 提示助词在书面语里的省略习惯

**L2 近代书面语句型** —— 漱石那个年代书面语的骨架：

- ～にほかならない、～ざるを得ない、～を余儀なくされる
- ～ともなれば、～とあれば、～からこそ
- ～べからず、～まじき
- ～つつある、～つつ、～ながら（も）
- ～において、～に関して、～をめぐって
- ～ものの、～とはいえ、～にもかかわらず

**L3 文语残存** —— 现代日语里还活着的古语（漱石用得比现代作家多得多）：

- ～き / ～けり（过去）
- ～べし（当然・义务）
- ～なり（断定・伝聞）
- ～ず（否定）、～ぬ
- ～たり（完了）
- ～む / ～ん（意志・推量）
- 漢文訓読調：～なりけり、～ぞ～ける

**L4 长句拆解方法** —— **这一层标准语法书都没有，但对用户最有用**：

《我是猫》难，不是难在单个语法点，而是**一句话裹了四层修饰**。
这一层每条不是"一个语法点"，而是"一种读法"：

- 找到"句末的谓语"（日语谓语在最后，先跳到句尾）
- 认出连体修饰块：从"最后一个用言"往回找它修饰的名词
- 处理插入句（～、（…）、～）
- 处理并列与省略（主语省略在日语里是常态）
- 把长句按"、」切开后逐块标注成分

> **L4 的 `connection` 字段怎么填**：填"适用场景"，比如
> 「句子里出现两个以上动词，且都在名词前面」。
> **`examples` 尤其重要** —— 要放**真的长句**（可以从公版书里摘，
> 但必须标 `source`），并逐块拆开写在 `note` 里。

### 7.4 顺序建议（重要：别从 N5 顺序写）

**不要**按 N5→N1 顺序写。理由是用户的**实际困难在书面语和长句**，
先把能立即改善阅读体验的做出来，比"补全 N5"更有价值。

建议顺序：

1. **L4 长句拆解（~10 条）** —— 最少条目、最大收益，先做
2. **L1 现代书面语基础（~60 条）** —— 常体 + 连体修饰是读原著的门槛
3. **L3 文语残存（~40 条）** —— 漱石高频，遇到就能查
4. **L2 近代书面语句型（~80 条）**
5. **JLPT 补齐（N5→N1）** —— 应试线，可以慢慢来

### 7.5 成本（实测数据，不是估计）

现有 10 条样例的实测体积：

| 指标 | 数值 |
|---|---|
| 整文件 | 9,052 字符（约 900 字符/条） |
| 其中教学内容 | 332 字符/条（74% 是中日文） |
| 换算 tokens | **约 400 tokens/条** |

**但这 10 条是"精简版"**（`detail` 只有 57 字、例句 3.3 条、易混 1 组、错误 2 条）。
做成能用的教材厚度要到 **2.5 倍**（`detail` 150-200 字、例句 4-5 条、易混 2-3 组、错误 3-4 条）。

所以四层约 190 条的预算：

| | 条数 | 输出 tokens | 含返工（×1.8） |
|---|---|---|---|
| 精简厚度 | 190 | ~76k | ~137k |
| **教材厚度（推荐）** | **190** | **~190k** | **~340k** |

> 参考：如果按最初设想的"全等级 JLPT 430~640 条"做教材厚度，
> 是 **770k~1150k tokens**。四层方案便宜一半以上，且更对症。

### 7.6 批量加内容的工作方式（2026-10 起用，已验证）

一次加 20 条以上时，**不要直接手写 JSON**。用这条流水线，原因和做法都记在这里：

1. 写一个**内容文件** `tools/内容-<层>.mjs`（例：`tools/内容-L3.mjs`）：
   只导出条目数组（纯 JS 对象，不是 JSON），外加一个可选的 `…_SOURCE` 来源说明。
   用 JS 而不是 JSON 的好处是可以在里面写注释，也可以少写 20 遍引号。
   内容多、以后还会继续加的层（L2、L3），**这个文件要留在仓库里**，
   它就是那一层的真相来源；跑完就一次性落地的批次（L1）可以不留。
2. 跑 `node tools/gen-grammar.mjs tools/内容-<层>.mjs`。
   它做三件事：
   - **生成前自检**：Markdown 星号、中文里混英文、例句里的 ASCII 空格、
     id 形状与唯一性、**一个内容文件的 level 必须统一**；
   - 合并进对应的等级文件（按 id 去重，已存在就跳过；可加 `--replace` 完全覆盖）；
   - 补上 `source` 字段。

   > ⚠️ **进哪个等级文件，是由条目自己的 `level` 字段决定的，不是由文件名猜的。**
   > 内容文件里写 `level: 'N3'` 就进 `N3.json`，写 `'N2'` 就进 `N2.json`。
   > 上一轮那 27 条 N3 的条目被塞进 `N5.json`，就是因为当时靠"文件名叫什么"来放
   > —— **让代码自己决定，不要靠人记。**
   >
   > ⚠️ 这个脚本名就是 `tools/gen-grammar.mjs`。**不要照着一个示例名去另建一个**：
   > 上一版 README 在这里写的是 `gen-语法-<层>.mjs`，而内容文件里又声称
   > 由 `gen-grammar-l3.mjs` 读取，那个文件根本不存在 ——
   > **文档和代码里各留了一句假话。** 教训：文档里写的路径必须真的存在。
3. `node tools/build-grammar-index.mjs` 重建索引。
4. `node tools/test-grammar.mjs` 跑数据层自检。
5. `node tools/qa-grammar.mjs` 在**真浏览器**里确认新内容真的长得出来。

> 这一轮（L1 第一批 27 条 + 第二批 16 条）就是按这个流程做的，生成前自检一次抓出真问题：
> 文案里的 `**`、id 里的大写字母、中文里混了英文单词。
> **先自己查一遍，比被测试打回来效率高**，因为报错信息能精确到是哪一条的哪个字段。
> 第二批（`tools/内容-L1b.mjs`，16 条）第一版写了 16 条、**条条带星号**，
> 生成前自检一次全部报出来 —— 这就是它存在的价值。
>
> ⚠️ **临时文件 vs 要留下的文件，判据是"这个层还会不会再加内容"**，不是"它是第几层"：
>
> | 文件 | 留不留 | 为什么 |
> |---|---|---|
> | `tools/gen-grammar.mjs` | **永远留** | 生成入口，带生成前自检；所有层都用它 |
> | `tools/内容-L3.mjs` | **留** | 文语这一层还要再补约 22 条 |
> | `tools/内容-L1b.mjs` | **留** | L1 还要再补约 17 条 |
> | `tools/内容-L1a.mjs`（第一批 27 条） | 删 | 一次性批次，内容已落进 `N3.json`，留着就是第二份真相 |
>
> ⚠️ **`tools/` 下 `_` 开头的临时文件，收工前一律删掉。**
> 但注意上表第一行那种"名字不带下划线、以后每批都要用"的工具**不算临时文件** ——
> 判据是"以后还用不用得上"，不是"这次任务是不是已经完成"。
>
> ⚠️ **文档里写的路径必须真的存在。** 上一版这里写的是 `gen-语法-<层>.mjs`，
> 而内容文件里声称由 `gen-grammar-l3.mjs` 读取，那个文件根本不存在 ——
> **代码和文档里各留了一句假话。** 现在 `check-deliverables.mjs` 会盯这一条。

> ⚠️ 四个踩过的坑（**前三个是同一个形状，所以放在一起看**）：
> · **全局字符串替换不认识语法。** 我用"删掉文件里所有 `**`"去清理强调标记，
>   结果把文件头的 JSDoc `/**` 也删了 —— 因为 `/**` 本身就是两个星号。
>   这个错**犯了三次**（L1 内容文件、L1 内容文件补收尾、L3 内容文件）。
>   最后一次还是"明知故犯"：心里想着"注释里的星号是单个的不会命中"，忘了开头就是两个。
>   **结论不是"把范围写对"，而是：不要用全局替换去改源码。**
>   要改文案就一处一处改，或者重写文件；要洗数据就洗**生成出来的 JSON**
>   （JSON 里除了字符串没别的，全局替换是安全的）。
> · **改结果不如改原因。** L3 那一批我先生成、再洗生成出来的 JSON —— 源文件里
>   还留着星号，下次谁再生成一次，脏东西就回来了。正确顺序是
>   **先把源文件改干净，再生成**。
> · **断言要对着真实界面写。** `qa-grammar.mjs` 第一版断言"页面上写着 47 条"
>   （界面故意不显示总数）、断言整句例句（界面会给例句自动加振假名，
>   汉字之间插进假名，整串永远匹配不上）、断言小标题是"常见错误"
>   （实际是"常见的错"）。三次都是断言错，不是界面错。
> · **断言要通过"故意改坏"来证明它有判别力**，而且**判别词不能随便挑**。
>   抓"标签搜索"那个 bug 的断言我写了三轮：第一轮用「文语」——**假判别词**，
>   标题里就写着"文语"，`title` 那支已经命中，改坏后照样绿；

   `tools/test-grammar.mjs` 的 `[7]` 节在盯这件事 —— **这条已经踩过三次**。
2. **中文讲解里不能混英文单词**（同一个 `[7]` 节在盯）。
3. **读音类说法必须自洽。** `[8]` 节盯着这条，因为真错过：
   原来写「は读作「わ」」——不准。は 这个假名本身读 ha，
   **只有当助词时**读 wa，而且**写法不变**。
   类似的坑：へ（助词读 e）、を（读 o）。
4. **不确定的知识点宁可写"这条我不确定"，也不要编。**
   用户是初学者，**无法发现我写错**，所以编造的成本全落在用户身上。
   一个可操作的做法：`detail` 里可以明确写「这条用法有争议，两种说法都有人用」。

#### ② 四大假定 —— 1 条归纳条 + 4 条老条目补标签

用户原话：「我搜了一下没有"四大假定"，这应该是一个比较常用的语法点才对。是不是没写完？」

- **查证结果：四个假定一条都不缺**，早就写好了
  （`n4-to-condition` 〜と、`n4-ba` 〜ば、`n4-tara` 〜たら、`n4-nara` 〜なら）。
- **缺的是「四大假定」这个说法本身**。搜索是拿关键词匹配 title / meaning /
  category / tags 的，而这四条标题写的是"必然的一…就…""书面味的只要…就…"，
  一个"假定"都没有 —— 所以用户搜不到，**以为没写完**。
- **这不是内容缺失，是可发现性缺失。** 两者要分开修，所以做了两件事：
  1. 新增归纳条 `n4-yon-dai-katei`。**归纳条不是把四个词再讲一遍**，
     而是给出**判定顺序**：先问后件能不能是意志，再问前件是话题还是发生了的事。
     四个词分开看时永远看不出"我该用哪一个"，归纳条解决的就是这个。
  2. 在那四条各自的 `tags` 里也加上「四大假定」，让它们单独被搜到时也能命中。
- ⚠️ **标签里同时放了简体和日文繁体**（`四大假定` / `四大仮定` / `仮定形`）：
  界面是简体中文，用户敲的是「四大假定」；但日文资料和输入法里写的是「四大仮定」。
  搜索是字符串直接 `includes` 匹配的，不同写法一条都搜不到 ——
  **实测搜「仮定」原本是 0 条**。两个都放，用哪种写法都能找到。
- 这一条**和它归纳的那四条放在同一个内容文件里**（`内容-JLPT-N4.mjs`），
  因为 `--replace` 是**按内容文件**为单位重跑的，放在一起它们必然一起进退，
  不会出现"归纳条说了四个词、其中两个已经改了"的不一致。

#### ③ 一词多义 —— 7 条，N5 3 + N4 2 + N3 2，分类「惯用型」

用户原话：「关于某些词汇的应用语法，我觉得也可以加进去，例如「かける」这种
一个读音对应很多意思的，具体涉及到的常用词汇有多少你自行判断。」

- **加之前是零覆盖**（搜 かける / 一词多义 / 多义词 都没有）。
- **选词标准**（"自行判断"的依据）：只收同时满足两条的词 ——
  ① 一个读音对应多个**词库里有独立条目**的词（不是同一个词的引申）；
  ② 这些意思在**日常阅读里都会遇到**。按这个标准筛出 6 个词：
  `かける`、`とる`、`あがる／のぼる`、`きく`、`みる`、`かかる`。
  它们的"多义"成因各不相同（词源不同 / 汉字不同 / 自他配对），正好覆盖三种情况。
- **这一批最要紧的写法：不能写成"かける 有 15 个意思"就完了。**
  用户是初学者，列一堆义项对他没有用 —— 他不知道**当前这句是哪个意思**。
  所以每一条都必须给**判定依据**：看助词（に 还是 を）、看搭配的名词
  （電話／時間／迷惑）、看有没有汉字（とる 写成 撮る 就一定是拍照）。
- **一个词的多义跨好几个等级，所以按等级拆成了三个文件**：
  `内容-JLPT-多义词-N5.mjs`（3 条）、`-N4.mjs`（2 条）、`-N3.mjs`（2 条）。
  为什么必须拆：gen-grammar 有一条硬规矩 —— **一个内容文件里的 `level` 必须统一**，
  否则"进哪个等级文件"就有歧义。而 `かける` 的"挂"是 N5、"添麻烦"是 N4。
  原始那份（`内容-JLPT-多义词.mjs`）保留完整说明，**改内容要改原始那份再重新拆**。

#### ④ 同时修掉的一个工具 bug：`--replace` 会抹掉别的批次的 `source`

- **现象**：`--replace` 原来直接写 `doc.source = source || doc.source`，
  意思是"我这次带了 source，所以文件级的 source 就换成我的"。
  结果用 `--replace` 单独重跑 N4 第二批之后，
  N4.json 里"N4 第一批／第二批／第三批"三行来源**只剩第二批一行**。
- **为什么必须修**：`source` 是**整个等级文件**累加出来的来源清单，
  而 `--replace` 只负责其中一个内容文件的那几条。来源是内容诚实性的一部分
  （§7.8、第五节），丢了就再也追不回来 —— 而且**不报任何错**。
- **修法**：只把**本文件负责的那几条**的来源替换掉，其余来源原样保留。
  做法是记录被移除条目各自的 `source`，把它们从清单里摘掉，再把新的追加进去。
- 修复后实测：`--replace` 重跑 N4 后 source 仍是三批都在，条目 0 丢失。

#### ⑤ 这一轮学到的两条写内容的硬规矩（已补进文件头注释）

1. **`mistakes` 里每一项必须是字符串，不是对象。**
   这一轮我按别处的习惯写成了 `{ wrong, right, why }`，结果被
   `String(obj)` 变成 `"[object Object]"` 混进中文检查里，
   报出来的是**「中文里混了英文：object Object」** ——
   报错信息完全指不到真正的原因，为此多花了一轮。
   ⚠️ 容易被 `confusions` 误导：**`confusions[]` 才是** `{ with, diff }` 对象。
2. **中文文案里不许出现罗马音或英文单词**（2 个以上连续字母就报），
   连 `NHK`、`vs` 都不行。想表达读音只能用**假名**。
   所以"浊音"那一批里所有说明都改写成了假名形式（把「读成 zi」改成「读成汉语拼音的资」）。
   同理 `examples[].ja` **不能有空格**，所以"て形总表"不能用
   「う・つ・る → って／った」这种表格式例句，只能拆成真正的词。

### 7.10 本轮：先审计再写（24 条，以及两条新的搜索/接续规则）

这一轮加了三批、合计 24 条。但比"加了多少条"更值得记的是**选条方式变了**。

#### ① 从"凭记忆挑"改成"先审计再写"

上一轮我差点犯一个错：准备写「ことにする」「ように」「ばかり」——
它们**早就有了**。语法库当时有 384 条（现在 **470** 条，跑
`node tools/sync-doc-counts.mjs` 拿实时数字），"我记不记得写过"完全不可靠。

所以这一轮的流程是：

1. 列出 N3 大纲里常见的约 57 个语法点；
2. 拿每个点的关键词去**全库搜**（搜 `title + meaning + category + tags + id`，
   不只是标题 —— 因为归纳条会在正文里提到别的点）；
3. **只写搜不到的**。

结果：57 个里 35 个已有覆盖、22 个真空缺。书面语线同理，20 个候选点里 9 个真空缺。
**这一步省下的不是时间，是避免往库里灌重复内容。**

⚠️ 这个审计有个**已知的粗糙处**，必须写下来：它只做**子串匹配**，
所以「ものだ」会因为 N2 有条「〜というものだ」而被判成"有覆盖"——
其实那个讲的是"讲道理"，和「〜ものだ」表"本该／真是"不是一回事。
**子串匹配会高估覆盖率。** 所以：

- 判成"缺"的可以**直接信**（子串都没命中，那是真没有）；
- 判成"有"的**还得人眼复核一遍**。

#### ② ⚠️ 新规则一：标题用汉字，tags 里必须补假名读音

这是本轮发现的**第二个"可发现性缺失"**（第一个是「四大假定」）。

现象：我写的标题是**汉字**（「〜と相まって」「〜気味」「〜がち」「〜だらけ」），
但**初学者看到的是读音**。他敲「あいまって」进搜索框 —— **0 条**；敲「相まって」才有。
同理「ぎみ」「がち」「だらけ」「ぶり」「たえない」都可能搜不到。

**这不是内容缺失，是搜索入口缺失。** 所以定成一条规矩：

> **凡是标题里有汉字的新条目，tags 里必须补上那个汉字的假名读音。**

本轮给 19 条补了读音标签，补完实测 42 个搜索词全部命中。

> 顺带记一个**我自己的误判**：我一开始搜「とあいまって」是 0 条，
> 差点当成"数据没进索引"去查管线。其实**正确读音是「と相まって」**，
> 是**我的搜索词写错了，不是库的问题**。
> 教训：**"搜不到"时先确认自己的关键词对不对，再怀疑数据。**

#### ③ ⚠️ 新规则二：补线性质的小批次**绝对不能带 `--replace`**

`gen-grammar.mjs --replace` 是按**内容文件**为单位替换的 ——
它会把这个内容文件负责的 id **先全部删掉**再重新加。

而 `N3.json` / `N2.json` 里**同时住着书面语线和应试线两批条目**。
所以像 `内容-L2补.mjs` 这种补线的小批次，一旦带 `--replace`，
只要 id 集合和文件里已有的条目重名，就会**静默删掉老条目**。

> 本轮这两批都是**不带 `--replace` 跑的**（新 id，本来也不重复）。
> 记这一条是因为它是**下一个最容易踩的坑**：
> `--replace` 的设计前提是"一个内容文件独占一个等级文件"，
> 而 N3/N2 已经打破了这个前提（见 §7.7 顶部那条警告）。

#### ④ 第四次踩同一个坑：Markdown 的星号又被写进了文案

`gen-grammar.mjs` 的生成前自检**一次报出 15 条**「文案里有 Markdown 标记」，
全是我写的两个星号。这个项目**没有 Markdown 渲染器**，文案走 `textContent`，
所以星号会**原样显示给用户看**。

**这已经是第四次了。** 所以记一条比"下次小心"可靠得多的做法：

> **写完文案之后，跑一句全局替换把两个星号删掉，再跑 gen-grammar。**
> 因为它在语义文案里**没有任何合法用途** ——
> 要么是 Markdown 强调（本项目禁用），要么是空指针解引用（那是代码，不该出现在这里）。
> 删掉一定安全。只处理 `export default` 之后的部分，别动文件头注释。

#### ⑤ 归纳条的第二次实践

上一轮定了「归纳条要给判定顺序，不给清单」。这一轮写了第二条：
`n3-j-hazureta-jokyou`「五个"没做到"的分工」。

它把**看起来互不相干**的五个说法收在一起：
わけにはいかない／ようがない／つもりだった／はずだった／べきだった。
共同点是它们都在回答同一个问题：
**"该做的／想做的／能做的"和"实际做到的"之间的落差在哪一侧**。

单独看这五条，初学者永远不知道该用哪个；放在一起就能看出各自堵的是哪个方向的落差。
**这个"找出共同问题"的思路可以推广。**

### 7.11 课堂笔记覆盖率审计：两个反直觉的发现

> 用户问"语法库完全覆盖了我课堂笔记里的内容吗"。
> 笔记 **220 条**语法点，逐条人眼比对不现实，所以先做机械审计。
> 产出是 `DOC/课堂笔记-覆盖率报告.md`（24 KB，可用 `tools/audit-notes.mjs` 重新生成）。
> 工程层面的记录见 `ARCHITECTURE.md` §二十七。

#### 发现一：⚠️ 最系统性的缺口是**最基础的东西**

这是完全反直觉的。笔记里缺得最系统的是：

> 动词ます形、动词的四种时态、动词三分类、は 与 が 的区别、五个基本形总览。
> **全是 N5 地基，一条都没有。**

原因：**"基础"被当成了"常识"**，写内容时默认"这还用写吗"。

但对初学者，这些恰恰最需要"有一条可查的东西"，而且**它们恰好是搜索量最大的词**。

> 📌 **本条最值得记**：
> **写内容按"难度"排序会漏掉地基，要按"用户会不会来搜"排序。**
> 一个知识点的价值 ≈ 它被搜的概率，而不是它的难度。

已补 5 条（`内容-N5基础.mjs`）。

#### 发现二：⚠️ 第三个"可发现性缺失"，这次栽在**空格**上

前两个分别是「四大假定」（差在说法）和假名读音（差在写法）。这个是第三个：

> **搜「は が 区别」返回 0 条** —— 而条目就在库里，标题是「は 与 が 的区别」。

两个原因叠在一起：

1. 搜索是 `includes` **精确子串匹配**，而"带空格分开写"恰恰是初学者最自然的输入
   （他就是在模仿语法书的写法「は と が の違い」）；
2. 标题里的**连接字「与」**让"去掉空白"也救不了它 —— **标题是给人读的，不是给搜索用的。**

两处修：匹配逻辑加"去空白再比一次"；数据在 tags 里补齐人们会敲的所有写法。

#### 顺带定下的一条数据规矩

> **凡是标题里有汉字或连接字的条目，tags 必须补上"用户真会敲的写法"。**
> 包括：汉字对应的**假名读音**（あいまって）、**带空格的写法**（は が）、
> **不带空格的写法**（はが）、以及该知识点的**常见说法**（四大假定／四大仮定）。

这条规矩一共来自三次踩坑（说法、读音、空格），所以它是三条里最具体的。

#### ⚠️ 机械审计的可信度必须标出来

抽查 56 个点后确认：**机械判定两个方向都会错**。

| 方向 | 例子 |
|---|---|
| 误判成"缺" | 笔记「たとえ〜ても」，库里明明有 `n3-j-tatoe-temo` |
| 误判成"有" | 笔记「ほど」，命中了 6 条含"ほど"的，但**没有一条是"没有比…更…"这个用法** |

所以报告里**机器结论和人工复核分成两节**，人工那节明确写"这节是手写的，比上面三张表可信"。
**机械审计的输出不能直接当结论。**

#### 本轮没能处理的部分（如实记）

- 笔记里的**副词／词汇类约 18 个点**（まだ・また、やはり、なかなか、全然、いくら…）：
  这些**不是句型语法**，塞进语法库会把"语法"这个分类搞浑。建议另开词汇类。
- A 表里剩下的"真缺但低频"点：`かしら`、`なぜなら`、`〜ずつ` 等。
  ⚠️ 但 `〜ば〜ほど` 和 `につれて／に従って` 是 **N3 高频**，
  它们的缺口严格说不属于"低频"，而是 **N3 应试线本身还没补完**。

> ✅ **上面这一条已经处理了**（见 §7.12）：
> `かしら`、`なぜなら`、`〜ずつ`、`につれて`、`に従って`、`からといって` 等
> 全部写进了 `tools/内容-JLPT-N3d.mjs`。

### 7.12 搜索审计法：用"两种搜法交叉"找真缺口（本轮定下来）

> 这一节记的是**怎么决定"下一个该写什么"**，
> 而不是写了什么。因为"凭记忆决定写什么"已经不可靠了 ——
> 库有 384 条，我记不清哪条写过。

#### 为什么需要审计：三次"准备写的东西早就有"

已经发生过三次：准备写的条目其实库里早有，写进去就是重复内容。
所以现在的规矩是 **先审计、再写**，不允许凭印象下笔。

#### ⚠️ 关键发现：**一种搜法不够，会漏，而且漏的方向还不一样**

本轮我写了两个审计脚本，它们**必须交叉使用**：

| 脚本 | 搜什么 | 错误方向 | 具体例子 |
|---|---|---|---|
| `tools/audit-gap.mjs` | 只搜结构化字段（title / meaning / category / id / tags） | **假有**（别的条目正文顺嘴提一句就算"有"） | 「になると」被 N4「〜と」的**例句**"春になると"命中 |
| `tools/search-json.mjs` | 搜**整个条目的 JSON 文本**（连例句、注意事项都算） | 更严，基本不假有 | 但它**只认字面**，写法一变就漏 |

**两个都搜不到的，才是真空缺。** 这一批写的就是这 15 个。

> 📌 **这条值得推广**：做"有没有覆盖"这类审计时，
> 宽松的判据会**假有**（漏掉真缺口），严格的判据会**假无**（重复劳动）。
> 只用一个必然出错 —— 因为它们的错误方向是**相反**的，交叉一下才对得上。

#### ⚠️ 第二个发现：「正文里提过一句」不等于「有一条能搜到的条目」

结构化搜索把 `くせして`（明明…却）和 `ずつ`（每…）判成了"已有" ——
因为别的条目正文里确实提到过它们。

**但对用户来说这不等于有：** 他搜「くせして」搜不到任何专门的条目，
只能看到一堆顺嘴提过它的别的语法点，那和没有是一样的。

> 📌 这是"可发现性 ≠ 内容覆盖"的**第四个例子**了
> （前三个：四大假定 / 假名-vs-汉字 / 「は が 区别」的空格）。
> **判据应该是"用户搜得到吗"，不是"库里提到过吗"。**

#### 本轮的两个真 bug（都是"不报错的静默失败"）

**① 多词查询恒返回 0 条**

用户很自然会敲「为什么 因为」这种两个词的查询。
原来的做法是把整串 `为什么 因为` 当一个词去 `includes` ——
没有任何条目含这五个连续字符（还带个空格），所以**恒为 0**。

> **用户越努力描述自己想找什么，越搜不到。** 这是最坏的一种失败方式。

改成"任一命中即算命中"（是**或**不是**与**），并按命中词数排序。
单词查询行为逐字节不变（一个词时，或＝与）。

**② `gen-grammar` 跳过同 id 条目，导致 tags 改动永远进不了数据文件**

这条更隐蔽。我在内容源文件里给老条目补了检索词，
`gen-grammar.mjs` 报"跳过已存在"，**数据文件没变**，
用户搜「四个假定」依然是 0 条 —— 表现是"我明明改了啊"。

修法：同 id 时**只合并 tags**（不覆盖正文，因为正文可能有后续人工修订），
合并只增不减，所以一定安全。

> 📌 **教训**：源文件和产物之间只要有"跳过"逻辑，
> 就存在**改了不生效**的静默路径。凡是有跳过的地方都要问一句：
> **"那我的修改怎么进去？"**

### 7.13 我写了一条重复的语法，而两个审计脚本都抓不住

> 这一节记的是**审计方法的边界**，不是内容。因为这次不是"漏了一条"，
> 而是"多了一条"，而"多"比"漏"更难查。

#### 事情经过

我写了 `n2-j-kuse-shite`（〜くせして）。
写完才发现 —— **`n3-j-kuse-ni`（〜くせに）里早就讲过它了**，
而且是作为"口语变体"放在易混对比里的。

也就是说：**同一个语法点，我写了两条。**

#### 为什么两个审计脚本都没抓住

它们查的是"**这个字符串**出现过没有"：

| 搜什么 | 结果 | 问题 |
|---|---|---|
| 搜「くせに」 | 搜不到「くせして」这四个字 | 字符串不同，互相搜不到 |
| 搜「くせして」 | 在 `くせに` 那条的**易混对比**里出现过 → 判"已有" | **结论碰巧对了，理由却不对** |

第二行特别值得注意：`search-json.mjs` 确实说了"已有"，
但它判"有"的依据是**"正文里提过一句"** ——
而这个依据在别的场合恰恰是错的（见 §7.12：`くせして`/`ずつ` 就是这样被判成"有"的）。

> 📌 **核心问题：审计按字符串，重复按语法点。这两件事之间有个缝。**
> 「くせに」和「くせして」是两个字符串，但**是一个语法点**。
> 任何只比对字符串的工具都看不见这件事。

#### 补法：让条目自己声明别名（`alias`）

新增一个字段 `alias`：**同一个语法点的其他写法**。

```js
{
  id: 'n3-j-kuse-ni',
  title: '〜くせに：明明…却（带责备）',
  alias: ['くせして'],        // ← 补的就是这条缝
  ...
}
```

有了它，工具就能**按语法点**查重，而不是按字符串。
`tools/check-grammar-dup.mjs` 做三类检查：

1. 同一别名被 ≥2 条同时声明 → **一定**是重复；
2. 一条把「X」声明为别名，而**另一条的标题主形式就是 X** → 疑重复；
3. 源文件和数据文件必须同步（只删一边 = 下次重跑又回来）。

同时 `alias` 也**参与搜索**（`build-grammar-index.mjs` 写进索引、
`grammarHit` 会查它）—— 所以用户搜「くせして」能找到讲 `くせに` 的那一条。

#### ⚠️ 一个失败的中间版本：别从标题里猜别名

第一版的 `check-duplicate.mjs` 是**从标题里按斜杠拆**出别名的
（因为本项目标题惯例是「〜A／〜B：说明」）。
结果报出 **77 组**"疑重复"，几乎全是假阳性：

| 假阳性 | 为什么它不是重复 |
|---|---|
| `n5-masu`(〜ます／〜ません／〜ました) ⟷ `n5-mashita`(ました／ません) | 同一个点**在不同难度分两级写**，这是语法书的分层讲解，不是重复 |
| 「なり」被 4 条 N2 文语条目共用 | 它们讲的是 `なり` 的**不同用法**（断定 / 列举 / なりに） |

> 📌 **标题是给人读的，里面的斜杠切分不等于"语法点身份"。**
> 所以最终版**只信显式声明的 `alias`，不猜**。
> 代价是"没声明 alias 的条目查不出重复"，但那比 77 条假阳性好得多 ——
> **一个天天误报的检查会被忽略，等于没有检查。**

#### 顺带修掉的一个连字符坑（同一个改动带出来的）

`relations.json` 和 `N5.json` 住在同一个目录里。
`build-grammar-index.mjs` 和 `test-grammar.mjs` 都用
`/^[A-Za-z0-9]+\.json$/` 找等级文件 —— 而**正则里那个点没转义时匹配任意字符**，
于是 `relations.json` 也被当成了等级文件：

- 索引里多出一个叫 `relations` 的"等级"（384 条语法却报"5 个等级"）；
- `test-grammar.mjs` 报两条莫名其妙的失败：`relations.json 有 items 且非空`。

> 📌 **一个转义符的错，不报错，只是多一个假等级。**
> 两处都改成 `\.json` 并显式排除，并且**加了断言卡死**这件事
> （`★ relations.json 没被当成等级文件`），反向验证过：改回去就红。

### 7.14 相关条目（`relations.json`）：把分散在不同难度的同一个点连起来

#### 为什么需要它

语法库是**按难度归档**的（见 §7.7 顶部那条警告）。带来的后果是：

> 同一个语法点在不同难度的讲法，**分散在不同文件、不同线里**，
> 用户看到其中一条时，**另外那些完全摸不到**。

具体例子 —— 「随着…」这条线有三条：

| id | 所在 | 形式 |
|---|---|---|
| `n3-j-ni-tsurete` | N3 应试线 | 〜につれて |
| `n3-j-ni-shitagatte` | N3 应试线 | 〜に従って |
| `n3-l1-to-tomo-ni` | N3 **书面语线** | 〜とともに／〜に伴って |

这三条本来应该互相看见 —— 而这正是**"语法是系统、不是孤点"**最该体现的地方。
用户读《我是猫》遇到 `とともに`，应该能一路摸到 `につれて`。

#### 数据放在哪、为什么

放在 `data/grammar/relations.json`，**不放进各条目的正文里**。

理由是：**关系是双向的**。如果 A 的正文里写"相关：B"，B 的正文里写"相关：A"，
那同一件事就有两个出处，改一边忘一边，就会出现"从 A 能跳到 B，从 B 跳不回 A"。
放在一个独立的表里，**一份数据同时约束两端**，才可能校验。

```json
{
  "relations": {
    "n3-j-ni-tsurete": [
      { "to": "n3-j-ni-shitagatte", "why": "常被混用：につれて 只能表「随着变化」，に従って 还能表「按照规矩」" }
    ]
  }
}
```

> ⚠️ 只存 `to`（id）和 `why`（一句话理由），**不存标题**。
> 标题由界面从索引里反查 —— 这样**改了标题不用同步改关系表**（去规范化）。

#### 三条硬规矩，由 `tools/check-related.mjs` 强制

| 检查 | 不检查会怎样 |
|---|---|
| `to` 的 id 必须真实存在 | 用户点进去是空白页，链接长得像能点 |
| 关系必须**双向** | 从 A 能跳到 B，从 B 跳不回 A → 用户觉得功能时好时坏 |
| **不能有重复键** | `JSON.parse` 遇到重复键**不报错**，后一个覆盖前一个 → 静默少几条关联 |

> ⚠️ 第三条我确实踩到了：`n3-j-kara-to-itte` 写了两遍，
> 而 `[1]~[5]` 全部通过 —— 因为被丢掉的那一份里没有坏数据。
> 一旦被丢掉的那份里**有**关系，就会静默少几条，**而且检查全绿**。
> 这类"解析器替你做了决定还不告诉你"的错最危险，所以单独查它。

#### 界面上长什么样

详情页底部会多一块「相关条目」，每条显示**目标条目的标题**（不是 id）
和那句 `why`，点一下就跳过去。
`qa-grammar.mjs` 的 `[9]` 段在真浏览器里验证：这块显示得出来、显示的是标题
（不是 id）、点得动、点完**真的换了一条**。

> ⚠️ 第一版这里有个 bug：`handleGrammarEntry` 只做了 `...item`，
> 而 `related` **只存在于索引里、不在等级 JSON 里** → 界面上整块不显示。
> 而数据层检查全绿，因为它查的是索引和 `relations.json`，**根本没经过这个接口**。
>
> 📌 **测试跑在同一条路上，才证明得了那条路通。**
> 所以补了 `qa-grammar.mjs` 的 `[9]`（真浏览器走完整接口）。
> 反向验证：把 `related` 改成 `[]`，3 条断言立刻变红。
